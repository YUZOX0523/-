# Gmail 返信要否判定 & 自動下書き生成システム 設計書

作成日: 2026-07-05
対象アカウント: y.tsutsumi@digirise.ai

## 1. 目的

受信メールの中から「返信が必要なもの」を自動で識別し、返信メールの下書き（Draft）を
Gmail 上に自動生成する。**送信は必ず人間が行う**（AIは下書きまで）。

- 毎朝メールを仕分ける時間を削減する
- 返信漏れを防ぐ
- 下書きがあることで返信のハードルを下げる（開いて微修正して送るだけ）

## 2. 全体アーキテクチャ

処理は4段のパイプラインで構成する。実行基盤が何であってもこの構造は共通。

```
┌──────────┐   ┌──────────────┐   ┌──────────────┐   ┌──────────────┐
│ ① 収集    │ → │ ② ルール除外   │ → │ ③ AI返信要否判定│ → │ ④ 下書き生成    │
│ 未読取得   │   │ no-reply等    │   │ LLMで分類      │   │ Draft作成+ラベル │
└──────────┘   └──────────────┘   └──────────────┘   └──────────────┘
```

### ① 収集（Fetch）

Gmail 検索クエリで対象を絞り込む。処理済みラベルが付いたスレッドは再処理しない（冪等性）。

```
in:inbox is:unread newer_than:2d
  -label:AI/下書き済 -label:AI/返信不要
  -category:promotions -category:social -category:forums
```

- `newer_than:2d` で直近分のみ。定期実行の間隔より十分広く取り、取りこぼしを防ぐ
- カテゴリ除外でプロモーション・SNS通知を API 呼び出し前に落とす

### ② ルールベース一次フィルタ（安い処理で先に落とす）

LLM に渡す前に、機械的に「返信不要」と断定できるものを除外する。

| ルール | 例 |
|---|---|
| 送信元が no-reply 系 | `no-reply@`, `noreply@`, `donotreply@`, `mailer-daemon@` |
| メーリングリスト/一斉配信 | `List-Unsubscribe` ヘッダあり、`list:` 該当 |
| 自動通知ドメイン | `@github.com`, `@notifications.google.com`, カレンダー招待通知 等 |
| 自分が送った下書き/送信済み | `in:draft`, `in:sent` を除外 |

除外したものには `AI/返信不要` ラベルを付けて次回以降スキップする。

### ③ AI による返信要否判定（Classify)

一次フィルタを通過したスレッドの本文を LLM に渡し、3値で分類する。

- **NEEDS_REPLY**: 自分宛の質問・依頼・日程調整・見積/契約などのやり取りで、
  スレッドの最後のメッセージが相手からのもの
- **NO_REPLY**: 情報共有のみ、CC で流れてきただけ、「ありがとうございました」で完結した会話
- **UNSURE**: 判断がつかないもの → 下書きは作らず `AI/要確認` ラベルだけ付ける

判定のシグナル（プロンプトに明記する判断基準）:

- To に自分のアドレスが入っているか（CC のみなら基本 NO_REPLY 寄り）
- 疑問文・依頼表現（「〜いただけますか」「ご確認ください」「いつがよろしいでしょうか」）の有無
- スレッドの最後の発言者が自分なら返信不要（ボールは相手側）
- 送信元が実在の人間か（署名・文面から判断）

### ④ 返信下書き生成（Draft）

NEEDS_REPLY と判定されたスレッドについて:

1. スレッド全文を取得し、文脈（過去のやり取り・相手との関係・敬語レベル）を把握
2. 返信本文を生成する
   - 相手の名前・宛名（「〇〇様」）を正しく入れる
   - これまでの自分の返信と同じトーン・署名スタイルに合わせる
   - **確定できない情報（日程・金額・可否判断など）は `【要確認: ○○】` プレースホルダにして
     勝手に約束しない**
3. 元メッセージへの返信として下書きを作成（`replyToMessageId` を指定し、
   スレッドに正しくぶら下げる。件名は `Re:` が自動で付く）
4. スレッドに `AI/下書き済` ラベルを付与

### ラベル設計

| ラベル | 意味 |
|---|---|
| `AI/下書き済` | 下書き生成済み。Gmail でこのラベルを見れば要対応メールが一覧できる |
| `AI/要確認` | 返信要否を判断できなかったもの（人間が見る） |
| `AI/返信不要` | AI が返信不要と判定したもの（誤判定の監査用） |

## 3. 実行基盤の選択肢

### 案A: Claude Code Remote のルーティン（推奨・コード不要）

このリポジトリの Claude セッションには既に Gmail MCP（検索 / スレッド取得 /
下書き作成 / ラベル操作）が接続済み。**新たな OAuth 設定・サーバー・コードが一切不要。**

- スケジュールトリガー（cron、例: 平日 8:00〜20:00 の毎時）で Claude セッションを起動
- セッションが上記①〜④のパイプラインをプロンプト（運用手順書）に従って実行
- 判定ロジックの変更 = 手順書の文言を直すだけ

| 観点 | 評価 |
|---|---|
| 初期コスト | ほぼゼロ（トリガー設定のみ） |
| 判定精度 | 高い（文脈を読んだ判定・下書き品質が高い） |
| 制約 | 実行間隔は最短1時間。リアルタイム性が必要なら案B |

### 案B: スタンドアロン実装（Node.js + Gmail API + Claude API）

完全に独立したサービスとして動かす場合。

- **構成**: Cloud Run Jobs / Cloud Functions + Cloud Scheduler（5〜10分間隔）
  または Google Apps Script（時間主導トリガー、GAS なら Gmail 認証が楽）
- **Gmail 認証**: OAuth2（`gmail.modify` スコープ）。GCP でプロジェクト作成・同意画面設定が必要
- **判定/生成**: Claude API（judge は `claude-haiku-4-5` で安く、下書き生成は上位モデル）
- **状態管理**: 処理済み管理は DB を持たず Gmail ラベルで行う（案Aと同じ設計）

| 観点 | 評価 |
|---|---|
| 初期コスト | 高い（OAuth 設定・デプロイ・監視） |
| リアルタイム性 | 高い（数分間隔、Pub/Sub push なら即時も可） |
| 向くケース | 分単位の即応が必要 / チーム全員のアカウントに横展開したい場合 |

**推奨**: まず案Aで運用を始めて判定基準を育て、間隔や規模が足りなくなったら
案Bに移行する（パイプライン設計は共通なので手順書がそのまま仕様書になる）。

## 4. 安全設計（ガードレール）

1. **自動送信は絶対にしない** — 生成するのは下書きのみ。送信ボタンは常に人間
2. **不確定情報は約束しない** — 日程・金額・可否は `【要確認】` プレースホルダ
3. **スキップリスト** — 経理・法務・特定ドメインなど「AIに触らせたくない」送信元を除外設定
4. **冪等性** — ラベルで処理済み管理。二重下書き・二重処理を防ぐ
5. **監査可能性** — `AI/返信不要` ラベルにより「AIが無視したメール」も後から確認できる

## 5. 運用フロー（ユーザー視点）

1. 毎時、自動で下書きが作られる
2. Gmail で `label:AI/下書き済` を開く（または下書きフォルダ）
3. 下書きを確認 → 必要なら修正 → 送信
4. 誤判定を見つけたら判定基準（手順書）に例外を追記して育てる

## 6. 段階的ロードマップ

| フェーズ | 内容 |
|---|---|
| Phase 1 | 案Aを手動起動で数日試し、判定精度と下書き品質を確認 |
| Phase 2 | cron トリガー化して毎時自動実行。Slack への日次サマリ通知を追加 |
| Phase 3 | 判定基準のチューニング（誤判定の例外ルール蓄積） |
| Phase 4 | 必要になれば案B（スタンドアロン）へ移行、チーム展開 |
