# ツールの2択と、自動化が伝わるデモの作り方

`CONFIG.choices` と `CONFIG.demos` を埋めるための指針。
前提として `service-philosophy.md` の**公式4レベル**を理解していること。

---

## 1. 企業が選ぶのは2つだけ

**前提として扱うツール**：ChatGPT / Claude / Copilot / Gemini / Claude Code / Codex

ただし**レベル1〜2の表示は Copilot / Gemini に統一する**（できることが大きく変わらないため、
片方に寄せる）。ChatGPT・Claude はレベル表やデモのツール表記には出さない。

```js
choices: {
  office: "both",   // "copilot" | "gemini" | "both"（両方併記・既定）
  agent:  "both",   // "claudecode" | "codex" | "both"（両方併記・既定）
}
```

**既定は `"both"`（両方併記）。** 提案先のグループウェアが読み取れたら片方に絞る。
読み取れないまま片方に決め打ちすると、商談で「うちは逆です」となり信用を落とす。
どちらでも到達レベルは同じなので、併記のまま見せても提案は成立する。

| 選択 | 何を選んでいるか | HPからの判断材料 |
|---|---|---|
| `office` | オフィスソフトの中で使うAI | 採用ページのメールドメイン／Googleフォームの利用／「Microsoft 365」「Teams」の記載／配布文書の形式 |
| `agent` | 業務プロセスを自動化するときのエージェント設計ツール | 情報システム部門の有無・技術スタック。判断材料がなければ `claudecode` |

**3つ目の選択肢を作らない。** `tools: [...]` のような多肢選択は旧仕様。使わない。

### トークン置換

デモの本文に `{{...}}` を書くと、選択に応じて自動で置き換わる。
**デモを2本に分ける必要はない。** 1本書けば両方の選択に対応する。

| トークン | copilot | gemini | both（既定） |
|---|---|---|---|
| `{{officeAI}}` | Copilot | Gemini | **Copilot / Gemini** |
| `{{officeSuite}}` | Microsoft 365 | Google Workspace | Microsoft 365 / Google Workspace |
| `{{sheet}}` | Excel | スプレッドシート | 表計算 |
| `{{doc}}` | Word | ドキュメント | 文書 |
| `{{mail}}` | Outlook | Gmail | メール |
| `{{chat}}` | Teams | Google Chat | チャット |
| `{{bot}}` | Copilot エージェント | Gem | Copilot エージェント / Gem |
| `{{nocode}}` | Copilot Studio ＋ VBA | GAS（Apps Script） | Copilot Studio / GAS |
| `{{agentAI}}` | Claude Code | Codex | Claude Code / Codex |

`both` では**ツール名は併記、個別アプリ名は一般名詞**にしている
（「Excel / スプレッドシートに集計して」は文中が冗長になるため「表計算に集計して」）。

**トークンの前後に半角スペースを入れない。** 日本語文中では
`{{mail}}に届いた` と書く（`{{mail}} に届いた` は併記時に「メール に届いた」と崩れる）。

デモの `needs` は表示するツール名を決める。**レベル1〜3は `"office"`、レベル4はエージェント設計なら
`"agent"`／ノーコードなら `"office"`。** 省略した場合もオフィスAI扱いになる。
**業務カードの `needs` は、紐づけるデモの `needs` と一致させる**（画面のツール表記が食い違うため）。

## 2. デモは4レベルを1本ずつ

**レベルが上がるほど「人が起動する回数」が減る。これがデモの軸。**

| Lv | デモで見せること | 到達感 |
|---|---|---|
| 1 基礎機能マスター | 手元のメモが共有できる形になる（Copilot / Gemini） | 毎回頼む |
| 2 ルーティンワーク効率化 | ボットを一度作り、部門で使い回す（Copilot / Gemini） | 仕組みを一度作る |
| 3 業務ツール連携 | メール→表計算→文書→チャットが一続きに動く | つないで一続きにする |
| 4 簡易コーディング・ワークフロー自動化 | **誰も起動していないのに動き、日をまたいで繰り返す** | 起動しなくても回る |

Lv4 は2本用意する。**エージェント設計（`needs:"agent"`）とノーコード自動化（`needs:"office"`）**。
開発部門がない企業でもレベル4に届くことを示すため、後者が重要。

**普通のチャット処理だけのデモは作らない。** レベル1でも必ず実務の成果物（議事録・次アクション）まで出す。

---

## 3. 自動化を伝える3つの装置

「自動化のイメージが湧かない」の原因は、**1回動いた話で終わっていること**。
自動化の本体は「毎日、誰も触らないのに繰り返し動く」ことなので、
**繰り返しを見せない限り伝わらない**。逆に、勝手に進む自動再生にすると速すぎて
説明できなくなる。**ボタン送りのまま、日をまたいだ繰り返しを見せる**のが答え。

### ① 1ステップずつボタンで進める（テンプレート側で実装済み）

デモは**「次へ」を1回押すごとに1ステップだけ進む**。勝手に進む自動再生は入れていない。
商談では説明しながら見せるため、**話す速度に合わせて止まっていること**が必要だからだ
（自動再生にすると、説明する側も聞く側も追えなくなる）。

`queue`（承認待ち）が出たら、**商談相手にボタンを押してもらう**。ここが半自動化の体感そのもの。

### ② `auto` — 日をまたいで繰り返す稼働タイムライン（レベル4に必須）

```js
{ kind:"auto", badge:"毎朝 7:00 自動実行",
  note:"ここから先は誰も操作していません。日をまたいで繰り返すのが自動化の本体です。",
  days:[
    { date:"8/18 月", events:[
        { at:"07:00:02", text:"スケジュール起動", t:"dim" },
        { at:"07:00:09", text:"検査記録を取り込み  1,042 行", t:"tool" },
        { at:"07:00:31", text:"研磨  Cpk=0.91（基準未満）", t:"warn" },
        { at:"07:00:38", text:"担当者へ通知を送信", t:"ok" } ],
      result:{ human:true, label:"通知1件", detail:"研磨工程 Cpk=0.91" } },
    { date:"8/19 火", events:[ ... ],
      result:{ human:false, label:"異常なし・通知0件", detail:"人の対応は不要" } },
  ],
  summary:"5営業日のうち、人の対応が必要だったのは2日。" }
```

- パネル内の**「翌日を実行する（残り N 日）」ボタンを押すごとに、1日分だけ**が流れる。
  押すたびに「はい翌日。誰も触っていません」と説明できる速さになっている
- 日付チップが順に点灯し、各日のログが1行ずつ流れ、その日の結果（人の対応が必要／不要）が出る
- **3〜5日分を入れる。** 1日だけでは「繰り返し動く」ことが伝わらない
- **人の対応が必要な日を、全体の一部だけにする。** 全日人が必要なら自動化に見えず、
  0日なら全自動に見えて不信を招く（5日中2日が目安）
- **異常がない日を必ず入れる。**「何も送らない」ことが設計であり、通知が読まれ続ける条件
- 時刻は `HH:MM:SS` 形式。行種別 `t` は `dim` / `tool` / `ok` / `warn`

### ③ `queue` — AIが用意し、人が承認する（半自動化の要）

承認待ちの一覧。**ボタンが実際に押せる。商談相手に押してもらう。**
`note` に「承認するまで社外へは出ません」のように、任せていない範囲を書く。
AIが用意するところまでを担い、人が承認する——この分担が半自動化の説明そのもの。

## 4. その他のステップ

| kind | 用途 | 主なフィールド |
|---|---|---|
| `note` | 状況説明・締めのひとこと | `text` |
| `prompt` | 人が入力する内容（タイプライター） | `cue`, `text` |
| `thinking` | 処理中の待ち | `text` |
| `builder` | ボット・自動化の設定フォーム | `title`, `fields[{k,v,files[]}]` |
| `chat` | 作ったボットを試す会話 | `name`, `turns[{who,text}]` |
| `handoff` | **人の工程がどれだけ減るか** | `before:{label,steps[]}`, `after:{label,steps[{t,by}]}`, `summary` |
| `flow` | エージェントの動作設計 | `title`, `steps[{t,d,gate}]` |
| `auto` | **自動実行タイムライン**（上記②） | `badge`,`note`,`days[]`,`summary` |
| `queue` | **承認待ちキュー**（上記③） | `title`,`note`,`items[{to,subject,body,conf}]` |
| `stats` | 稼働実績・利用実績のKPIタイル | `title`,`note`,`items[{k,v,u,hi}]` |
| `kpi` | 導入前後の比較 | `title`,`items[{k,before,after,delta}]` |
| `rollout` | 部門への横展開ボード | `title`,`items[{dept,note,pct}]` |
| `doc` / `bullets` / `sheet` | 生成された文書・箇条書き・表 | — |
| `term` / `diff` | ターミナル出力・コード差分 | — |

### 台本の型

```
Lv1: note → doc（元データ）→ prompt → thinking → bullets → ai → note
Lv2: note → prompt → builder → thinking → chat → stats → ai → note
Lv3: note → prompt → thinking → sheet → doc → handoff → ai → note
Lv4（エージェント）: note → prompt → handoff → flow → auto → queue → stats → ai → note
Lv4（ノーコード）  : note → prompt → builder → auto → stats → ai → note
```

### 必ず守る5点

1. **レベル4に `auto` を必ず入れる。** これが無いと自動化のイメージが湧かない
2. **`handoff` の人の工程を0にしない。** 全自動の絵は不信を招く。1〜2工程は人に残す
3. **`flow` の `gate`（人の判断）を2つ以上置く**
4. **最後は `ai` か `note` で締める。** AIの出力で終わらせず、人の判断・組織への還流で終わる
5. **提案先の固有名詞を入れる。** 品番・工程名・部門名・規程名

各デモに `why`（このデモで何が変わるかの一文）を必ず書く。画面下に出て営業のカンペになる。

---

## 5. 画面表現の禁止事項

- 各社の**ロゴマークを模倣しない**。`app` はトークンでサービス名を入れる
- 実在しない機能を描かない。「ボタン1つで全自動」は使わない
- 画面下の「◯◯／再現イメージ」注記と、上部の「画面はすべて再現イメージです」バッジを**消さない**
- 出力に実在の取引先名・個人名を入れない
- **エージェントが承認なしに社外へ送る**描写をしない

## 6. よくある失敗

| 症状 | 原因 | 直し方 |
|---|---|---|
| 「もう知っている」と流される | 普通のチャット処理だけを見せている | Lv2以上のデモに進む |
| **「自動化のイメージが湧かない」** | `auto` が無く、1回動いた話で終わっている | **`auto` を入れ、「翌日を実行」を何回も押して繰り返しを見せる** |
| 「速すぎて分からない」と言われる | デモを自動再生にしている | 1ステップずつボタンで進める（テンプレートは既にこの形） |
| 「半自動化がピンとこない」 | AIと人の分担が絵になっていない | `queue` を入れて、相手に承認ボタンを押してもらう |
| 「うちには無理」と言われる | レベル4がエージェント設計だけになっている | ノーコード版（`{{nocode}}`）のデモも見せる |
| 「本当に続くのか」と疑われる | 一度動いた話で終わっている | `stats` で30日の稼働実績を出す |
| 「怖い」と言われる | 人の判断が絵にない | `flow` の `gate` と `handoff` の「人」工程を明示する |
