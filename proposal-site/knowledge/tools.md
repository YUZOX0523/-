# ツールの選び方と、再現デモの作り方

`CONFIG.tools` と `CONFIG.demos` を埋めるための指針。
前提として `service-philosophy.md` の**到達レベル**を理解していること。

---

## 1. デモの中心は「チャットボット作成」と「エージェント設計」

**普通のチャット（プロンプトを打って答えが返る）は絶対にデモにしない。**
それはもう誰でも知っており、しょぼい印象を与えて逆効果になる。

デモが実演すべきものは、2つのサービスの差そのもの。

| デモの層 | `layer` | 実演内容 | どのサービスの到達点か |
|---|---|---|---|
| Layer 1 | `"base"` | **業務専用チャットボットを作って同僚に配る** | 法人リスキリング365（全社員） |
| Layer 2 | `"core"` | **業務プロセスをAIエージェントに設計する** | AI人材養成講座（推進人材） |

画面上では2層が別のグループとして並び（セクション03）、**デモ自体が2層構造の証明**になる。

### Layer 1（365）のデモで見せること

- **ノーコードであること** — 指示文を書き、参照資料を指定するだけ
- **10分程度で作れること** — 事務職の方でも到達できる水準だと伝わること
- **同僚に配れること** — 公開範囲を設定し、部門の型がボットに溜まっていく
- **答えない範囲を先に決めること** — 「規程に無いことは人事へ案内する」など。ここが安心して配れる条件
- 作ったボットを**実際に試すチャット**まで見せる（`builder` → `chat` の流れ）

### Layer 2（養成講座）のデモで見せること

「自動化・半自動化のイメージが湧く」ことが最重要。**設定画面を見せるだけでは伝わらない。**
次の4点を必ず含める。

1. **人の工程がどれだけ消えるか**（`handoff`）— 今の8工程 → 人が触るのは1〜2工程。
   これが一番速く伝わる。**人の工程を0にしない**（全自動の絵は不信を招く）
2. **誰も操作していないのに動いている**（`runlog`）— 時刻つきの稼働ログ。
   ヘッダーに「毎朝7:00 自動実行」バッジ。`title` に「誰も操作していません」と書く
3. **AIが用意し、人が承認する**（`queue`）— 承認待ちキュー。**ボタンが実際に押せる**。
   商談相手に押してもらうのが最も効く。「承認するまで社外へは出ない」を明示
4. **続いている証拠**（`stats`）— 30日の稼働実績。
   「自動実行30回／人を呼んだ回数7回」のように、**人の介入が少ないことを数字で**示す

加えて：動作設計（`flow`）に `gate`（人の判断）を2つ以上／権限の境界（`diff`）／
過去データでの検証結果。

## 2. ツールの選択

`CONFIG.tools` に入れた ID のものだけが表示される。カードもデモも自動で絞られる。

| ID | 表記 | Layer 1（ボット作成） | Layer 2（エージェント設計） | 選ぶ判断材料（HPから読む） |
|---|---|---|---|---|
| `gemini` | Gemini（Google Workspace） | カスタムAIを作る | Apps Script と組み合わせて自動化 | 採用ページのメールが Google 系／Google フォーム利用 |
| `copilot` | Copilot（Microsoft 365） | エージェント（ボット）を作る | Copilot Studio ＋ Teams 承認 | Office文書配布／「Microsoft 365」「Teams」の記載 |
| `claudecode` | Claude Code | （Layer 2 専用） | データ分析・監視・既存資産の解読 | 情報システム部門がある／測定データを持つ |
| `codex` | Codex | （Layer 2 専用） | システム連携・業務処理の実装 | 自社開発・基幹システムの記載／エンジニア採用 |

**判断できないときの既定**：`["gemini", "copilot"]`。
これだけで Layer 1／Layer 2 の両方が成立する（開発部門がなくてもエージェントは組める）ため、
最も多くの企業に当てはまる。商談冒頭で「Google と Microsoft のどちらをお使いですか」と聞き、
その場で片方を消す運用でよい。

`claudecode` / `codex` を足すのは、**情報システム部門が明確にある企業**のみ。
役割が近いので両方入れるのは避ける（どちらか1つ）。**合計3つまで**。

## 3. ステップの型（`step.kind`）

| kind | 用途 | 主なフィールド |
|---|---|---|
| `note` | 画面外の状況説明・締めのひとこと | `text` |
| `prompt` | 人が入力する内容（タイプライター表示） | `cue`, `text` |
| `thinking` | 処理中の待ち。**自動で次へ進む** | `text` |
| `builder` | **ボット設定フォーム**（Layer 1 の主役） | `title`, `fields[{k,v,files[]}]` |
| `chat` | **作ったボットを試す会話** | `name`, `turns[{who:"user"｜"bot",text}]` |
| `flow` | エージェントの動作設計 | `title`, `steps[{t,d,gate}]` |
| `handoff` | **人の工程がどれだけ減るか**（Layer 2 必須） | `before:{label,steps[]}`, `after:{label,steps[{t,by:"human"｜"agent"}]}`, `summary` |
| `runlog` | **時刻つき稼働ログ＝自動で動く実感**（Layer 2 必須） | `badge`, `title`, `lines[{time:"07:00:02",text,t}]` |
| `queue` | **承認待ちキュー。ボタンが実際に押せる**（半自動化の要） | `title`, `note`, `items[{to,subject,body,conf}]` |
| `stats` | **稼働実績・利用実績のKPIタイル** | `title`, `note`, `items[{k,v,u,hi}]` |
| `ai` | AIの応答パネル。**設計意図・注意点を書く場所** | `text` |
| `doc` | 文書ウィンドウ（改行はそのまま反映） | `title`, `body` |
| `bullets` | 箇条書きの成果物・検証結果 | `title`, `items[]` |
| `sheet` | 表計算の画面（旧デモ由来。使ってよい） | `head[]`, `rows[][]`, `total[]` |
| `term` | ターミナル出力（`claudecode` / `codex`） | `lines[{t,text}]` |
| `diff` | コード差分（`codex`） | `file`, `lines[{t,text}]` |

`term` の行種別：`cmd`（`$`付き・タイプライター）／`tool`（青）／`ok`（緑）／`dim`（灰）／省略で通常。
`diff` の行種別：`add`（緑）／`del`（赤）／`ctx`（文脈）。

### 台本の型

**Layer 1（ボット作成）— 8ステップ**
```
note（誰が何のために作るか・所要時間10分）
→ prompt（やりたいこと）
→ builder（名前／役割の指示／参照資料／公開範囲。「入力するのはこれだけ」と書く）
→ thinking
→ chat（作った本人ではなく別の同僚が使っている場面にする）
→ stats（配布後の利用実績。部門で回っている証拠）
→ ai（運用のコツ・答えない設計にした理由）
→ note（365へ事例登録すると他部門が真似できる）
```

**Layer 2（エージェント設計）— 8〜10ステップ**
```
note（誰が設計するか・講座の何か月目か）
→ prompt（設計の依頼。任せたくない範囲も一緒に言う）
→ handoff（人の工程 8 → 1〜2）
→ flow（動作設計。gate を2つ以上）
→ diff（開発系のみ／権限の境界を見せる）
→ runlog（誰も操作していない稼働ログ）
→ queue（承認待ちキュー。ボタンを押してもらう）
→ stats（30日の稼働実績。人を呼んだ回数が少ないこと）
→ ai（検証で分かったこと・人に残した判断）
→ note（成果物が組織資産として残る／365へ戻る）
```
非開発系（gemini / copilot）は `diff` を省く。`queue` は「人が承認する」業務のときに入れる。

### 必ず守る5点

1. **`handoff` と `runlog` を必ず入れる。** これが無いと自動化のイメージが湧かない
2. **`handoff` の人の工程を0にしない。** 全自動の絵は不信を招く。1〜2工程は人に残す
3. **`flow` の `gate` を2つ以上置く。** 人が判断する箇所がないエージェントは、この提案では誤り
4. **最後は `ai` か `note` で締める。** AIの出力で終わらせず、人の判断・組織への還流で終わる
5. **提案先の固有名詞を入れる。** 品番・工程名・部門名・規程名。汎用サンプルは一瞬で嘘に見える

`runlog` の書き方：時刻は `HH:MM:SS` 形式。`badge` に「毎朝 7:00 自動実行」「常時監視・自動実行」、
`title` に「◯月◯日のログ ／ 誰も操作していません」。異常がない日は通知しない設計にする
（毎日通知が届く絵は「読まれなくなる」ため逆効果）。

### デモの数

**選択したツール1つにつき、対応する層で1本ずつ。** 合計4〜6本。
多いほうが良いわけではない。商談で見せるのは**1〜2本**だけ。
各デモに `why`（このデモで何が変わるかの一文）を必ず書く。画面下に出て営業のカンペになる。

## 4. 画面表現の禁止事項

- 各社の**ロゴマークを模倣しない**。`app` には「Gemini」「Copilot」「Copilot Studio」のように
  サービス名のみを入れ、テンプレート側が汎用のスパークルアイコンを添える
- 実在しない機能を描かない。「ボタン1つで全自動」は使わない
- 画面下の「◯◯／再現イメージ」注記と、上部の「画面はすべて再現イメージです」バッジを**消さない**
- 出力に実在の取引先名・個人名を入れない
- **エージェントが社外へ何かを送る**描写をしない（承認を経る設計として描く）

## 5. よくある失敗

| 症状 | 原因 | 直し方 |
|---|---|---|
| 「もう知っている」と流される | 普通のチャット処理を見せている | `builder`＋`chat` か `flow` に置き換える |
| 「イメージが湧かない」と言われる | 設定画面と設計図だけで、動いている画面がない | `runlog`（自動で動くログ）と `handoff`（人の工程が減る絵）を足す |
| 「半自動化がピンとこない」 | AIと人の分担が絵になっていない | `queue` を入れて、相手に承認ボタンを押してもらう |
| 「本当に続くのか」と疑われる | 一度動いた話で終わっている | `stats` で30日の稼働実績を出す |
| 「うちには無理」と言われる | Layer 1 でノーコードだと伝わっていない | `builder` の中身を具体的にし、所要時間を `note` で書く |
| 「怖い」と言われる | `gate` がなく、AIが勝手に動く絵になっている | 人の判断を `gate` で明示し、権限の境界を `diff` か `flow` で見せる |
| 2つのサービスの違いが伝わらない | デモが片方の層しかない | 各層に最低1本ずつ置く |
| 数字を突っ込まれて答えられない | 検証結果の数字が整合していない | 内訳の合計を電卓で検算する |
