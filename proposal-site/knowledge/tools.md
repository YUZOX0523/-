# 導入AIツールの選び方と、再現デモの作り方

`CONFIG.tools` と `CONFIG.demos` を埋めるための指針。

---

## 1. ツールの選択

`CONFIG.tools` に入れた ID のものだけが画面に出る。カードもデモも自動で絞り込まれるため、
**検討していないツールは消すだけでよい**（該当する業務カードも一緒に消える）。

```js
tools: ["gemini", "copilot"],          // Google Workspace 中心の会社
tools: ["copilot", "claudecode"],       // M365 + データ処理まで踏み込む会社
tools: ["gemini", "copilot", "claudecode", "codex"],  // 全部見せる（初回の幅出し）
```

| ID | 表記 | 何に効くか | 選ぶ判断材料（HPから読む） |
|---|---|---|---|
| `gemini` | Gemini（Google Workspace） | 文章・資料・調査。Gmail / ドキュメント / スプレッドシート / Meet の中で完結 | 採用ページのメールが `@gmail` / Google フォーム利用 / 「Google Workspace」の記載 |
| `copilot` | Copilot（Microsoft 365） | 同上を Outlook / Word / Excel / Teams の中で。既存Excel資産が多い会社に強い | 問い合わせが `@outlook`/独自ドメインでOffice文書配布 / 「Microsoft 365」「Teams」の記載 |
| `claudecode` | Claude Code | データ分析、既存資産（マクロ・スクリプト）の解読、突合・集計の自動化 | 情報システム部門がある / Excelマクロ運用の匂い / 検査・測定データを持つ |
| `codex` | Codex | 社内ツールの開発、システム間連携、既存システムの改修 | 自社開発・自社システムがある / 「基幹システム」の記載 / エンジニア採用 |

**判断できないときの既定**：`["gemini", "copilot"]` の2つ。
グループウェアが読み取れなければ、02の業務カードは両方のツールを混ぜておき、
商談の冒頭で「Google と Microsoft のどちらをお使いですか」と聞いて、その場でどちらかを消す。

**ツールは3つまでを推奨**。4つ並べると「何から始めるのか」が伝わらなくなる。
`claudecode` と `codex` は役割が近いので、両方入れるのは情報システム部門が明確にある会社だけ。

---

## 2. デモ台本の作り方

1つのデモは「1つの業務が終わるまで」を6〜9ステップで描く。原則は3つ。

1. **入力から始めて、判断で終わる。** 最後は AI の出力ではなく、`ai`（AIの注意書き）か
   `note`（人が判断する旨）で締める。AIが全部やってくれる話に見せない。
2. **具体的な固有名詞を入れる。** 品番・部門名・日付・数量。提案先の商材名を使う。
   汎用的な「サンプルデータ」は一瞬で嘘だと分かる。
3. **数字は必ず整合させる。** 表の合計、前月比、件数の内訳。1箇所でも合わないと全体が疑われる。

### ステップの型（`step.kind`）

| kind | 用途 | 主なフィールド |
|---|---|---|
| `note` | 画面外の状況説明・締めのひとこと（グレーの注記で表示） | `text` |
| `prompt` | 人がAIに入力する内容（タイプライター表示） | `cue`（"入力" / "Copilot" など）, `text` |
| `thinking` | 処理中の待ち。**自動で次のステップへ進む** | `text` |
| `ai` | AIの応答パネル。**注意点・確度の低い箇所を書く場所** | `text` |
| `doc` | 文書ウィンドウ。改行はそのまま反映される | `title`, `body` |
| `bullets` | 箇条書きの成果物（議事録・指摘事項など） | `title`, `items[]` |
| `sheet` | 表計算の画面 | `head[]`, `rows[][]`, `total[]` |
| `term` | ターミナル出力（`claudecode` 用） | `lines[{t,text}]` |
| `diff` | コードの差分（`codex` 用） | `file`, `lines[{t,text}]` |

`term` の行種別 `t`：`cmd`（`$` 付きコマンド・タイプライター表示）/ `tool`（ツール実行行、青）/
`ok`（成功、緑）/ `dim`（補足、灰）/ 省略時は通常テキスト。
`diff` の行種別 `t`：`add`（緑）/ `del`（赤）/ `ctx`（文脈行）。

### チューニング済みの台本の型

**`gemini` / `copilot`（事務系）**
```
note（状況）→ doc または sheet（元データ）→ prompt（依頼）→ thinking
→ doc / sheet / bullets（成果物）→ ai（注意点）→ note（人の判断が残る旨）
```

**`claudecode`（分析・解読系）**
```
term（起動）→ prompt（依頼）→ term（ファイル読み込み・スクリプト生成）→ thinking
→ term（実行結果の数値）→ ai（解釈と、確認すべきこと）→ note（次回は一言で済む旨）
```

**`codex`（開発系）**
```
prompt（要望）→ term（既存構成の確認・生成・テスト）→ diff（実際の変更）
→ term（PR作成 または 実行結果）→ ai（設計意図）→ note（取り込みは人が判断する旨）
```

### デモの数

- **選択したツール1つにつき2本**。多いほうが良いわけではない。商談で全部見せる時間はない。
- 業務カードの `demo` から飛ばせるので、1本のデモを複数のカードから共有してよい。
- 各デモに `why`（このデモで何が変わるかの一文）を必ず書く。画面下に表示され、
  営業が説明を思い出すためのカンペになる。

## 3. 画面表現の禁止事項

デモ画面は**再現イメージ**であり、各社の実画面ではない。以下は必ず守る。

- 各社の**ロゴマークを模倣しない**。`app` には「スプレッドシート」「Outlook」のように
  アプリの一般名を入れる。テンプレート側が汎用のスパークルアイコンを添える。
- 実在しない機能を描かない。「ボタン1つで全自動」のような表現は使わない。
- 画面下に自動で「◯◯（サービス名）／再現イメージ」の注記が入る。**消さない。**
- デモ上部の「画面はすべて再現イメージです」バッジも**消さない。**
- 出力に実在の取引先名・個人名を入れない（提案先自身の情報も、公開情報の範囲に留める）。

## 4. よくある失敗

| 症状 | 原因 | 直し方 |
|---|---|---|
| デモが「すごいけど自分には関係ない」と見られる | 業務が汎用的すぎる | `title` と `prompt` に提案先の商材名・工程名を入れる |
| 「本当にこんなにうまくいくのか」と疑われる | `ai` ステップで注意点を書いていない | 確度の低い箇所・人が確認すべき箇所を必ず1つ書く |
| ステップが長くて途中で飽きられる | 10ステップ超 | 6〜9に削る。元データの提示は1つに絞る |
| 表の数字を突っ込まれて答えられない | 合計・前月比が合っていない | 公開前に電卓で検算する |
