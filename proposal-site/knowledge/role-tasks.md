# 職種・職位別 業務変化カタログ

`CONFIG.departments` を埋めるための素材集。**そのままコピペしない。** 提案先HPから読み取った
事業内容の語彙（商材名・工程名・顧客の呼び方）に必ず言い換えてから使う。
「見積書」ではなく「図面ベースの個別見積」、「顧客対応」ではなく「入居者からの修繕依頼」のように、
その会社の人が日常で使っている言葉になっているかを基準にする。

---

## 1. 書き方の原則

業務カード1枚は `title` / `before` / `after` / `hours` / `tool` / `demo` で構成する。

| 項目 | ルール | 悪い例 | 良い例 |
|---|---|---|---|
| `title` | 業務名。動詞で終わる具体的な単位業務にする | 「営業DX」 | 「図面ベースの見積作成」 |
| `before` | **人の動作**で描く。数字（所要時間・件数）を1つ入れる | 「非効率な状態」 | 「類似案件を過去ファイルから探し、単価と工数を転記して積み上げる。1件40〜60分」 |
| `after` | AIの出力で終わらせず、**人が何に時間を使うか**で締める | 「AIが自動で見積を作成」 | 「たたき台が生成され、担当者は妥当性の判断だけを行う」 |
| `hours` | 1人あたり週の削減時間。**保守的に**。下表の下限寄りを取る | 8.0 | 3.0 |
| `tool` | `CONFIG.tools` に含まれるものだけ。含まれないカードは自動で非表示 | — | — |
| `demo` | 対応する `CONFIG.demos` の `id`。無ければボタンは出ない | — | — |

**禁止事項**
- 「AIが判断します」と書かない。判断は人に残す設計であることが、この資料の信頼性の土台。
- 人員削減を示唆する表現（「◯名分の人件費が不要に」）を使わない。削減時間は振り替え先があるものとして扱う。
- 断定形（「〜になります」）ではなく想定形（「〜できます／〜する想定です」）で書く。

### 職位ごとに見る場所を変える

同じ部門でも、職位によって「効く場所」が違う。`roles` の付け方はここで決まる。

| 職位 | 関心 | AIが効く業務の型 |
|---|---|---|
| `exec` 経営層 | 判断材料が揃っているか | 情報収集・一次調査、部門横断のデータ統合、会議資料の下書き |
| `mgr` 管理職 | 部下の状況が見えるか、文書に時間を取られていないか | 報告・稟議・評価などの文書化、進捗の要約、計画の組み替え案 |
| `staff` 担当者 | 手を動かす時間そのもの | 転記・検索・集計・下書き作成、定型応答 |

現場作業者（製造・物流・店舗）は「作業そのもの」は減らない。**記録・報告・転記**に絞って書く。
ここを盛ると一気に嘘っぽくなるので、`hours` は 0.5〜1.2 に収める。

## 2. 週あたり削減時間の目安（1人あたり・保守見積）

`CONFIG.roi.rows.hours` と各カードの `hours` はこの範囲に収める。

| 対象 | 目安 | 根拠になりやすい業務 |
|---|---|---|
| 経営層 | 1.5〜3.0h | 資料の下書き、情報収集 |
| 管理職 | 2.0〜4.0h | 文書作成、報告の要約、計画立案 |
| 営業・事務・企画 | 2.0〜3.5h | 見積・メール・議事録・集計 |
| 専門職（士業・医療・設計） | 2.0〜4.0h | 調査、下書き、記録 |
| 現場作業（製造・物流・店舗） | 0.5〜1.2h | 日報・記録・転記のみ |
| 技術・情報システム | 3.5〜5.0h | 開発、調査、データ処理、既存資産の解読 |

部門ごとの人数は、HPの組織図・採用ページ・従業員数から推定する。合計が公表従業員数を超えないこと。
推定できない場合は「対象◯◯名（全◯◯名中）」と絞り、対象外の人数は試算に入れない。

## 3. 共通部門カタログ（業種を問わず出てくる）

### 経営・企画
- **月次経営会議の資料づくり** — 各部門のExcelを手作業で統合 → 統合・要約・グラフ・前月比コメントまで下書き（`copilot` / `gemini`）
- **市場・競合の情報収集** — 都度検索して個人メモで止まる → 論点を決めて一次調査、出典付き要約（`gemini`）
- **稟議・社内通達の作成** — 過去文書を探して体裁を真似る → 要点を渡すと草案、判断根拠の記述に集中（`gemini` / `copilot`）
- **予算・実績の差異分析** — 数字を並べ替えて眺める → 差異の大きい項目と要因候補を先に提示（`copilot`）

### 営業
- **見積・提案書の作成** — 過去案件を探して転記 → 実績の型に沿ったたたき台、担当者は妥当性判断（`gemini` / `copilot`）
- **問い合わせの一次回答** — 都度過去メールを検索して返信文を書く → 受信箱内で下書き、事実確認と送信のみ（`copilot`）
- **訪問記録と次アクション** — 個人ノートで止まり共有されない → 議事録・次アクション・共有文まで整う（`gemini`）
- **顧客ごとの状況整理** — 担当者の頭の中にしかない → 履歴を要約して引き継ぎ可能な形に（`copilot`）

### カスタマーサポート・受付
- **問い合わせの分類と一次回答** — 内容を読んで担当に振り分け → 分類と回答候補を自動で用意、人は確認（`copilot` / `gemini`）
- **FAQ・マニュアルの整備** — 更新が追いつかず古い情報が残る → 実際の問い合わせから更新差分を起こす（`gemini`）
- **応対記録の入力** — 通話後に記憶を頼りに要約入力 → 記録から要約と分類を生成（`copilot`）

### 管理部門（経理・人事・総務）
- **請求・支払データの突合** — 目視照合。件数が多い月は残業 → 差分抽出を自動化し例外だけ見る（`claudecode`）
- **社内規程の問い合わせ対応** — 担当者が規程を読み直して個別回答 → 回答補助を用意し最終確認だけ（`copilot`）
- **採用・評価の文書作成** — 毎回ゼロから書き、粒度が人により揺れる → 要件から粒度の揃った草案（`gemini`）
- **経費・稟議のチェック** — 全件を目視 → ルール違反候補の抽出、人は判定だけ（`claudecode`）

### マーケティング
- **コンテンツ制作** — 企画から公開まで担当者1人に依存 → 構成案と初稿を並行生成、人は事実確認と編集（`gemini`）
- **顧客データの分析** — 分析できる人がおらず勘で判断 → 集計・可視化を組み立てて実行（`claudecode`）

### 技術・情報システム
- **古い社内資産の解読と仕様化** — 中身を知る人がおらず触れない → 処理の意図と仕様書を起こす（`claudecode`）
- **現場向け小規模ツールの開発** — 着手まで数ヶ月、Excel運用でしのぐ → その日のうちに動く試作（`codex`）
- **システム間のデータ連携** — 手作業のCSV運用、担当者が休むと止まる → 自動化しエラー時だけ人が見る（`codex`）
- **障害・問い合わせの一次調査** — ログを目で追う → ログを読ませて原因候補を絞る（`claudecode`）

## 4. 業種別の固有業務

HPから業種を判定し、共通カタログに**その業種固有のものを2〜3件混ぜる**。
固有業務が入っているかどうかが「うちのことを分かっている」と感じてもらえる分かれ目。

### 製造業
- 図面ベースの個別見積（`gemini`）
- 検査データのばらつき分析・工程能力の把握（`claudecode`）
- 是正処置報告書・顧客提出書類の下書き（`copilot`）
- 日報・作業記録の脱・紙運用（`codex`）
- 技能・段取りノウハウの言語化と手順書化（`gemini`）
- 生産計画の組み替え案づくり（`copilot`）

### 建設・不動産
- 積算・拾い出しの下ごしらえ（`gemini`）
- 施工写真・日報の整理と報告書化（`copilot`）
- 入居者・施主からの問い合わせ一次対応（`copilot`）
- 物件情報の掲載原稿づくり（`gemini`）
- 是正・安全パトロール記録の集計（`claudecode`）

### 卸売・小売
- 発注・在庫データの異常検知（`claudecode`）
- 商品説明・POP原稿の量産（`gemini`）
- 店舗別売上の要因分析（`copilot`）
- 取引先とのメール・条件整理（`copilot`）

### 運輸・物流
- 配車・積載計画の案出し（`copilot`）
- 点検・運行記録の脱・紙運用（`codex`）
- 荷主からの問い合わせ一次回答（`copilot`）
- 遅延・事故報告書の下書き（`copilot`）

### IT・通信・SaaS
- 仕様書・設計書の下書きとレビュー（`claudecode`）
- 既存コードの調査・影響範囲の特定（`claudecode`）
- 顧客向けリリースノート・ヘルプ記事の作成（`gemini`）
- 障害の一次切り分け（`claudecode`）
- 機能開発そのものの速度（`codex`）

### 医療・福祉
- 記録・申し送りの下書き（`copilot`）※患者個人情報の取り扱いは必ずQ&Aで触れる
- 加算・書類要件のチェック（`copilot`）
- シフト・人員配置の案出し（`copilot`）
- 家族向け説明文書の作成（`gemini`）

### 専門サービス（士業・コンサル）
- 調査・リサーチの一次まとめ（`gemini`）
- 顧客向け報告書の構成と初稿（`gemini`）
- 契約書・規程のレビュー観点の洗い出し（`claudecode`）
- 面談記録から論点整理（`gemini`）

### 金融・保険
- 稟議・審査資料の下書き（`copilot`）
- 顧客向け説明資料の作成（`gemini`）
- 規制・ガイドライン改定の影響整理（`gemini`）
- データの突合・異常検知（`claudecode`）

### 教育
- 教材・課題の作成と難易度調整（`gemini`）
- 保護者向け通知文の作成（`gemini`）
- 成績・出欠データの集計と傾向把握（`copilot`）

### 飲食・宿泊
- 予約・問い合わせの一次対応（`copilot`）
- メニュー・館内案内の多言語化（`gemini`）
- 売上・客数の要因分析（`copilot`）
- シフト作成（`copilot`）

## 5. カード数の目安

| 部門数 | 1部門あたりのカード | 合計 |
|---|---|---|
| 5〜7部門 | 3枚（職位が分散するように `roles` を振る） | 15〜21枚 |

- 各部門で `exec` / `mgr` / `staff` のどれを選んでも**1枚以上出る**ように `roles` を配る。
  0枚になる組み合わせは「今回の想定には含めていません」と表示されるが、多発すると手抜きに見える。
- 提案先で明らかに存在しない部門は入れない（工場を持たない会社に「製造現場」を出さない）。
