# 効果試算のルールと想定質疑ライブラリ

---

## 1. 試算の考え方

この資料の数字は「金額を確定させるため」ではなく、**桁が合っているかと、どの部門から
着手する価値が大きいかを判断してもらうため**にある。だから前提はすべて画面に開示する。

### 計算式（テンプレートに実装済み）

```
部門ごとの年間削減時間 = 対象人数 × 1人あたり週削減時間 × 47週 × 定着率
合計削減時間           = 部門の合計
人件費換算             = 合計削減時間 × 時間単価
正社員換算             = 合計削減時間 ÷ 1,880時間
```

### 設定値

```js
roi: {
  weeksPerYear: 47,      // 稼働週数。祝日・休暇を引いた保守値。変えない
  hourlyRate: 3800,      // 時間単価の初期値。業種平均で置く（画面上でスライダー操作可）
  scenarios: [           // 定着率。順番を変えない（先頭が初期表示になる）
    { id:"cons", label:"保守的", rate:0.30, note:"一部の関心の高い方から定着する段階" },
    { id:"std",  label:"標準",   rate:0.50, note:"部門ごとに使い方が共有された段階" },
    { id:"amb",  label:"積極",   rate:0.70, note:"日常業務の標準手順に組み込まれた段階" },
  ],
  rows: [ { dept:"sales", heads:46, hours:2.5 }, ... ],  // dept は departments の id
}
```

### 守るルール

- **初期表示は必ず保守シナリオ（定着30%）。** ヒーローの数字もこれで計算される。
  最初に大きい数字を見せて後から言い訳する構成にはしない。
- `heads` の合計は**公表従業員数を超えない**。推定できない部門は入れず、
  プロフィールに「対象◯◯名（全◯◯名中）」と書く。
- `hours` は `role-tasks.md` の目安表の**下限寄り**を取る。現場作業者は 0.5〜1.2h。
- **時間単価は業種平均で置き、商談中に相手の実額へ動かしてもらう。**
  スライダーを一緒に動かす行為そのものが「押しつけていない」ことの証明になる。
- **投資額（ライセンス・導入支援費）は載せない。** `roi.costNote` で
  「ご提案資料でご案内します」と明示する。ここで金額を出すと、提案本番の役割がなくなる。
- 「人件費が◯◯万円削減できます」と言い切らない。`assumptions` に
  「削減された時間がそのまま人件費の削減になるとは限らない」を**必ず残す**。

### 時間単価の目安（初期値）

| 業種 | 目安 |
|---|---|
| 製造・建設・運輸 | 3,500〜4,000円 |
| 卸売・小売・飲食・宿泊 | 3,000〜3,500円 |
| IT・専門サービス・金融 | 4,500〜6,000円 |
| 医療・福祉・教育 | 3,500〜4,500円 |

（法定福利費を含む人件費ベース。迷ったら 3,800円）

## 2. 想定質疑ライブラリ

`CONFIG.qa` は**6〜8問**。多すぎると読まれない。提案先の業種で出やすいものを選ぶ。
回答は「できます」で終わらせず、**条件と、デジライズがどう関与するか**まで書く。

### 必ず入れる4問

**Q. 社外のAIに、自社の情報を入れて大丈夫なのか**
> 法人向けプランでは、入力した内容がAIの学習に使われない設定が標準です。そのうえで
> 「入れてよい情報／だめな情報」の線引きを社内ルールとして決めることをお勧めしています。
> デジライズではこのルール策定から支援します。技術的な設定と運用ルールの両方が揃って
> 初めて安全になる、という考え方です。

*医療・福祉・金融の場合は、業種固有の規制（個人情報・要配慮情報・監督指針）に触れる一文を足す。*

**Q. 現場が使ってくれるか自信がない**
> 最も多いご相談です。全社一斉に配るより「困っている業務が明確な数名」から始めたほうが
> 定着します。本サイトの02で挙げた業務は、その最初の対象を選ぶための材料としてお使い
> いただけます。定着状況は使用頻度と業務数で測り、進捗を可視化しながら進めます。

**Q. 04の数字はどこまで信じてよいのか**
> 公開情報からの想定であり、実データではありません。前提はすべて画面上に開示しています。
> 目的は金額の確定ではなく、桁が合っているか・どの部門から着手する価値が大きいかを
> ご判断いただくことです。実データをお預かりできれば精度の高い試算をお出しできます。

**Q. まず何から決めればよいか**
> 本日は「02の業務変化のイメージが合っているか」だけご確認いただければ十分です。
> 合っていれば、対象部門とツールを仮決めし、次回のご提案でスケジュールと投資額を
> ご説明します。

### 状況に応じて選ぶ

**Q. 効果はどのくらいの期間で出るか**
> 文章作成・要約・調査は1〜2週間で体感できることが多いです。業務の手順そのものを
> 変える取り組みは3〜6ヶ月を見ていただく必要があります。短期と中期を並行させる
> 進め方をご提案しています。

**Q. すでに一部で使っている。重複しないか**
> 重複しません。既にお使いの範囲を確認し、その延長として設計します。多くの企業で
> 「個人が便利に使っている」段階から「業務手順として定着している」段階への移行が
> 課題になっており、そこが私たちの主な支援領域です。

**Q. ツールは結局どれを選べばよいか**
> 既にお使いのグループウェアに合わせるのが基本です。Google Workspace なら Gemini、
> Microsoft 365 なら Copilot が自然です。社内システムやデータ処理に踏み込む場合は
> Claude Code や Codex を組み合わせます。本サイトの03は、貴社でご検討中のものだけを
> 表示しています。

**Q. 内製化したい。依存関係にならないか**
> 内製化を前提に設計します。社内で推進する方を決めていただき、その方が自走できる
> 状態をつくることをゴールにしています。研修・伴走支援・ルール整備を組み合わせ、
> 最終的に私たちが抜けても回る形を目指します。

**Q. 情報システム部門がない／人手が足りない**
> 専任部門がない企業でも進められる範囲から着手します。02のうち文書・調査系の業務は
> 情報システム部門の関与なしに始められます。システムに踏み込む部分は、
> 私たちが手を動かす形でご支援します。

**Q. うちの業界は特殊で、AIには無理ではないか**
> 業界特有の判断そのものをAIに任せることは想定していません。判断の前段にある
> 情報を集める・整える・書き起こすという作業を対象にしています。02のカードで
> 「AI活用後」の欄が判断で終わっているのは、そのためです。

**Q. 現場のPCが古い／スマートフォンが配布されていない**
> ブラウザが動く環境であれば利用できます。端末や回線の制約は、着手する部門を
> 選ぶ際の条件として扱います。現場作業者向けの取り組みは後半に置くことが多いです。

**Q. 従業員が「仕事を奪われる」と感じないか**
> 02の削減時間は、人員を減らすための数字として扱っていません。多くの場合、
> 手が回っていなかった業務に振り替わります。この点は導入時の社内説明で最も
> 重要なところなので、説明の仕方も含めてご支援します。

### 書き方の注意

- 一人称は「私たち」または「デジライズ」。「弊社」は使わない（ページ全体の文体に合わせる）。
- 「絶対に」「必ず」「100%」を使わない。
- 答えられない質問は載せない。載せた質問は商談で必ず深掘りされる。
