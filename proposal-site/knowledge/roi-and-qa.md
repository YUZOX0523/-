# 効果試算のルールと想定質疑ライブラリ

---

## 1. 試算の考え方

この資料の数字は「金額を確定させるため」ではなく、**桁が合っているかと、どの部門から
着手する価値が大きいかを判断してもらうため**にある。だから前提はすべて画面に開示する。

### 計算式（テンプレートに実装済み）

```
部門ごとの年間削減時間 = 対象人数 × 1人あたり週削減時間 × 47週 × 定着率
合計削減時間           = 部門の合計
人件費換算             = 合計削減時間 × 時間単価
正社員換算             = 合計削減時間 ÷ 1,880時間
```

### 設定値

```js
roi: {
  weeksPerYear: 47,      // 稼働週数。祝日・休暇を引いた保守値。変えない
  hourlyRate: 3000,      // 時間単価の初期値。提案資料の試算と揃えてある
  scenarios: [           // 定着率。順番を変えない（先頭が初期表示）
    { id:"cons", label:"保守的", rate:0.30, note:"一部の関心の高い方から定着する段階" },
    { id:"std",  label:"標準",   rate:0.50, note:"部門ごとに使い方が共有された段階" },
    { id:"amb",  label:"積極",   rate:0.70, note:"日常業務の標準手順に組み込まれた段階" },
  ],
  rows: [ { dept:"sales", heads:46, hours:2.5 }, ... ],  // dept は departments の id
}
```

`rows` の `dept` は `CONFIG.departments` の `id` と対応させる。`heads` の合計が
「対象人数」として画面に出るため、プロフィールの「対象◯◯名」と一致させる。

### 守るルール

- **初期表示は必ず保守シナリオ（定着30%）。** ヒーローの数字もこれで計算される。
  最初に大きい数字を見せて後から言い訳する構成にはしない
- `heads` の合計は**公表従業員数を超えない**。推定できない部門は入れず、
  プロフィールに「対象◯◯名（全◯◯名中）」と書く
- `hours` は `role-tasks.md` の目安表の**下限寄り**を取る。現場作業者は 0.8〜1.2h
- **時間単価は業種平均で置き、商談中に相手の実額へ動かしてもらう。**
  スライダーを一緒に動かす行為そのものが「押しつけていない」ことの証明になる
- 「人件費が◯◯万円削減できます」と言い切らない。`assumptions` に
  「削減された時間がそのまま人件費の削減になるとは限らない」を**必ず残す**
- 品質向上・属人化の解消・技能承継は時間換算しにくいため**含めず、含めていない旨を明記する**

### 投資額は書かない。公的支援の存在だけ示す

`roi.costNote` は「投資額を提案資料へ送る」ための文。金額・補助率・上限・助成額は**書かない**。
代わりに、実質負担を圧縮できる制度が2つあることだけを伝える。

| 制度 | 対象 |
|---|---|
| デジタル化・AI導入補助金 | 法人リスキリング365（2年契約の利用料が補助対象経費） |
| 人材開発支援助成金 | AI人材養成講座（受講費用。企業規模で助成額が変わる） |

必ず添える注記：**申請・審査がある／同一経費への重複適用はできない**。

### 時間単価の目安（初期値）

| 業種 | 目安 |
|---|---|
| 製造・建設・運輸 | 3,000〜3,500円 |
| 卸売・小売・飲食・宿泊 | 2,750〜3,250円 |
| IT・専門サービス・金融 | 4,000〜5,500円 |
| 医療・福祉・教育 | 3,000〜4,000円 |

（法定福利費を含む人件費ベース。提案資料の試算は3,000円。迷ったら3,000円）

## 2. 想定質疑ライブラリ

`CONFIG.qa` は**8〜10問**。回答は「できます」で終わらせず、
**条件と、デジライズがどう関与するか**まで書く。

### 絶対に書いてはいけない答え

> ✕「全社一斉に配るより、困っている業務が明確な数名から始めたほうが定着します」

**これはサービスの思想の否定にあたる。** 使う人だけに配ると社内に断層ができ、
推進人材が成果を出しても横に広がらない。**全社基盤（365）は全社員に配るのが原則**で、
その中から推進人材を選ぶ。「少数から始める」という表現は使わない。

「小さく始める」という言い方も避ける。正しくは
**「全社に基盤を配り、推進テーマを絞って始める」**。配る範囲は絞らない。

> ✕「まず365で基盤を作り、そのあと推進人材を育てます」

**段階論も誤り。** 2つのサービスは**同時にスタートし、並行して走らせる**（垂直立ち上げ）。
順番にやると基盤づくりの数か月は成果がゼロのまま投資だけが先行する。同時に立ち上げれば、
推進人材が出した成果をその時点で全社が受け取れる。

### 必ず入れる5問（このサービス固有の論点）

**Q. 研修は過去にもやりましたが、続きませんでした。今回は何が違うのですか。**
> 一度きりの研修で終わらせないことが、このサービスの設計の中心です。法人リスキリング365は
> 動画教材が継続更新され、レベル別ワークショップは参加し放題、相談できるオンラインサロンも
> 付いています。学び続ける場が常にある状態にします。さらにAI人材養成講座で推進人材が実務
> テーマの成果を出し、その成果物を365へ戻すことで、次の人が真似できる教材になります。学習が
> 単発のイベントではなく、業務の一部として回り続ける構造にしています。

**Q. 全社員に配る必要はありますか。使う人だけでよいのでは。**
> 使う人だけに配ると、社内に「使う人」と「使わない人」の断層ができます。そうなると推進人材が
> 成果を出しても横に広がらず、結果として投資が回収できません。全社員に基盤を配ることと推進
> 人材を育てることは、順番ではなく同時に進めます。同時だからこそ、推進人材が出した成果をすぐ
> 全社の学習資産として還流できます。365は学習・利用状況が見えるので、次の推進候補もデータで
> 見つかります。

**Q. 全員がレベル4まで到達する必要がありますか。**
> 必要ありません。全員を専門家にする設計ではなく、役割を分ける設計です。100名の会社であれば、
> 70名が日常業務で使い（レベル1〜2）、30名が推進・成果創出を担う（レベル3〜4）という形が基本です。
> この2つは段階ではなく、同時に立ち上げる役割分担です。大切なのは人数比そのものではなく、
> 成果が全社に還る導線が通っていることです。

**Q. 推進人材に選ぶ社員が思い当たりません。**
> AIに詳しい人を探す必要はありません。選抜の軸は技術経験ではなく、業務理解・実行力・共有力・
> 成果志向です。現場の課題を言葉にでき、小さく試して前に進め、周囲を巻き込める方が適しています。
> 候補が固まっていなくても構いません。全社基盤の立ち上げと並行して進めるため、365の学習・利用
> データから次の候補者が浮かび上がってきます。

**Q. デモのようなことを、本当に自社の社員ができるようになりますか。**
> 前半のチャットボット作成は、プログラミングを使いません。指示文を書き、参照する資料を指定
> するだけです。365の動画とワークショップで、事務職の方でも到達している範囲です。後半の
> エージェント設計は6か月の養成講座で、実務テーマに沿って伴走しながら進めます。講座終了時には
> 学習履歴ではなく、業務棚卸し表・実装成果・効果測定・横展開パッケージという、実務で検証した
> 成果が会社に残ります。

### 状況に応じて選ぶ

**Q. 社外のAIに、自社の情報を入れて大丈夫なのでしょうか。**
> 法人向けプランでは、入力した内容がAIの学習に使われない設定が標準です。そのうえで「入れてよい
> 情報／だめな情報」の線引きを社内ルールとして決める必要があります。365にはAIセキュリティの
> 学習コンテンツと、自社版ガイドラインの策定支援が含まれています。技術的な設定と運用ルールの
> 両方が揃って初めて安全になる、という考え方です。

*医療・福祉・金融の場合は、業種固有の規制（要配慮情報・監督指針）に触れる一文を足す。*

**Q. うちの社員は忙しくて、学習の時間が取れません。**
> 日常利用層に求めるのは、まとまった研修時間ではありません。動画は短く分かれており、ワーク
> ショップは任意参加です。まず自分の業務に直結する1つを試すところから始まります。推進人材には
> 6か月で一定の時間を確保していただく必要があるため、対象者の選定と時間の確保は貴社にお願い
> する役割としてお伝えしています。

**Q. 導入すると、社内の負担はどれくらいになりますか。**
> 教材の更新、ワークショップの運営、利用促進、実装の伴走、データの可視化はデジライズが担います。
> 貴社にお願いするのは、経営テーマの提示、対象者の選定、現場調整の3つです。専任者を置く必要は
> ありませんが、意思決定できる方が窓口になっていただけると進みが早くなります。

**Q. 効果はどのくらいの期間で出ますか。**
> 日常業務の下書き・要約・調査は1〜2週間で体感できることが多いです。チャットボットを作って
> 配る段階は1〜3か月、業務プロセスをエージェントに設計する段階は3〜6か月を見ていただきます。

**Q. 数字はどこまで信じてよいものですか。**
> 公開情報からの想定であり、実データではありません。前提はすべて画面上に開示しています。目的は
> 金額の確定ではなく、桁が合っているか・どの部門から着手する価値が大きいかをご判断いただく
> ことです。実データをお預かりできれば、精度の高い試算をお出しできます。

**Q. すでに一部でAIを使っています。重複しませんか。**
> 重複しません。既にお使いの範囲を確認し、その延長として設計します。多くの企業で「個人が便利に
> 使っている」段階から「業務手順として定着している」段階への移行が課題になっており、そこが
> 私たちの主な支援領域です。レベル2以上に置いている業務が、その移行にあたります。

**Q. 情報システム部門がありません。**
> 専任部門がなくても進められます。エージェント設計は Google Workspace や Microsoft 365 の
> 標準機能の範囲で組めるものも含まれています。開発が必要な範囲は私たちが手を動かす形で
> ご支援します。

**Q. 従業員が「仕事を奪われる」と感じないでしょうか。**
> 削減時間は、人員を減らすための数字として扱っていません。多くの場合、手が回っていなかった
> 業務に振り替わります。この点は導入時の社内説明で最も重要なところなので、説明の仕方も含めて
> ご支援します。推進人材を社内から育てる設計にしているのも、外から人を入れて置き換えるので
> はないというメッセージになります。

**Q. 内製化したいのですが、依存関係になりませんか。**
> 内製化を前提に設計しています。推進人材を社内から育て、その方が自走できる状態をつくることが
> 養成講座のゴールです。講座終了時には業務棚卸し表・実装成果・効果測定・横展開パッケージが
> 会社に残るため、私たちが抜けても次のテーマを自社で回せます。

### 書き方の注意

- 一人称は「私たち」または「デジライズ」。「弊社」は使わない
- 「絶対に」「必ず」「100%」を使わない
- 投資額・助成金額の数字を答えに入れない（「ご提案資料でご案内します」で止める）
- 答えられない質問は載せない。載せた質問は商談で必ず深掘りされる
