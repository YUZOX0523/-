# /proposal-site — 提案前フックサイト生成

営業が**提案資料を出す前**に見せる1ページのアーティファクトを作る。
目的は契約でも見積提示でもなく、「AI活用後の自社の姿がイメージでき、費用対効果が
期待できそうだ」と感じてもらい、その場で質疑ができる状態にすること。

**目標作成時間 10分。** 迷ったら既定値で進める。完璧さより、商談に間に合うことを優先する。

## 参照ファイル

作業前に必要なものだけ読む（全部読まなくてよい）。

| ファイル | 読むタイミング |
|---|---|
| `proposal-site/templates/proposal-site.html` | 必ず。これをコピーして CONFIG を書き換える |
| `proposal-site/knowledge/role-tasks.md` | 業務カードを書くとき（毎回） |
| `proposal-site/knowledge/tools.md` | デモ台本を書くとき（毎回） |
| `proposal-site/knowledge/roi-and-qa.md` | 試算とQ&Aを書くとき（毎回） |
| `proposal-site/knowledge/design-brand.md` | 色の判断に迷ったとき / ロゴ・デザインの可否を確認するとき |

## 入力

ユーザーからは最低限これだけ受け取れればよい。

- **必須**: 提案先のコーポレートサイトURL
- **任意**: 導入検討ツール（`gemini` / `copilot` / `claudecode` / `codex` から複数選択）
- **任意**: 分かっている情報（従業員数、部門構成、聞いている課題、商談相手の職位）

URLだけ渡された場合は**確認せずに進める**。ツール未指定なら `["gemini","copilot"]` を既定とし、
HPから Google Workspace / Microsoft 365 の手がかりが読めればそちらに寄せる。
成果物を出した後に「ツールはこの2つにしました。変える場合は言ってください」と添える。

## 生成フロー

### 1. コーポレートカラーを抽出する

```bash
node proposal-site/scripts/brand-color.mjs <提案先URL>
```

推奨値をそのまま `CONFIG.brand.color` に使う。ただし：

- 出力が「△ 要調整」なら、彩度を保ったまま明度を下げた同系色に差し替える
- 抽出できない／モノトーンの会社は濃紺 `#1F3A5F`
- 蛍光色・原色はそのまま使わず彩度を落とす

外部取得が失敗する環境では `WebFetch` でHPを読み、記述されている色や
ロゴの色から判断してよい（`--stdin` で保存済みHTMLを渡す方法もある）。

### 2. HPを読んで事業を理解する

`WebFetch` で以下のページを読む（あるものだけ。多くて4ページ）：

- トップページ / 事業紹介 — 何を作って誰に売っているか、商材名・工程名の語彙
- 会社概要 — 従業員数、拠点、設立
- 採用ページ — **部門構成が最もよく分かる。職種一覧は職位設計の直接の材料になる**
- 社長メッセージ / ニュース — 直近の関心事（人手不足、技能承継、海外展開など）

ここで拾った**その会社の言葉**を、以降のすべての文言に使う。
「顧客対応」ではなく「入居者からの修繕依頼」のように言い換えられているかが品質を決める。

読み取れなかったことは**推測で埋めず「想定しました」と明記する**。
01セクションは「この理解が合っているかご確認ください」という構成になっており、
ズレの指摘がそのまま商談の会話になる設計。

### 3. テンプレートをコピーして CONFIG を書き換える

```bash
cp proposal-site/templates/proposal-site.html /tmp/<任意の名前>-proposal.html
```

出力先は作業ディレクトリ外（スクラッチパッド等）にする。**テンプレート本体は上書きしない。**

書き換える順番：

1. `<title>` — 提案先の業務に即した固有名。**社名は入れない**（例「精密加工現場のAI変化マップ」）
2. `CONFIG.brand.color` — 手順1の値
3. `CONFIG.company` — `eyebrow` / `title`（`<span class="hl">` で1語だけ強調）/ `lead` /
   `profile`（社名が特定されない属性のみ）。`notice` と `footMeta` は基本そのまま使う
4. `CONFIG.premise.facts` — HPから読み取った4項目。各項目に `src`（出典ページ名）を必ず付ける
5. `CONFIG.tools` — 検討ツールのみ残す。含まれないツールのカード・デモは自動で非表示になる
6. `CONFIG.departments` — 5〜7部門 × 各3枚。`role-tasks.md` の共通カタログ＋業種固有を2〜3件
7. `CONFIG.demos` — 選択ツール1つにつき2本。`tools.md` の台本の型に沿う
8. `CONFIG.roi` — `rows` の `dept` は departments の id と一致させる。`heads` 合計は従業員数以下
9. `CONFIG.qa` — 6〜8問。`roi-and-qa.md` の必須4問＋業種で選ぶ
10. `CONFIG.next` — 基本そのまま。日程が決まっていれば `when` を実日付にする

### 4. 検算する

公開前に必ず確認する（ここを飛ばすと商談で数字を突っ込まれる）：

- [ ] デモの表の合計・前月比・件数の内訳が計算上合っている
- [ ] `roi.rows` の `heads` 合計 ≤ 公表従業員数、かつプロフィールの「対象◯◯名」と一致
- [ ] `departments` の各部門で、`exec`/`mgr`/`staff` のどれを選んでも1枚以上カードが出る
- [ ] `demos` の `id` と、カードの `demo` が全部対応している
- [ ] `roi.rows` の `dept` が `departments` の `id` と全部対応している
- [ ] 社名がどこにも入っていない（`<title>` 含む）
- [ ] 実在の取引先名・個人名が入っていない

JS の構文チェック（CONFIG編集で壊しやすい）:

```bash
node -e 'const s=require("fs").readFileSync("<出力ファイル>","utf8");const m=s.match(/<script>([\s\S]*)<\/script>/);new Function(m[1]);console.log("OK")'
```

### 5. アーティファクトとして公開する

`Artifact` ツールで公開する。`favicon` は 🧭 固定（提案先ごとに変えない）。
`description` は「業種・規模の提案先向け／部門×職位の業務変化と再現デモ」の一文。

公開後、ユーザーに以下を渡す：

1. アーティファクトのURL
2. **商談での使い方**（3行）— 01で理解のズレを確認 → 02で相手の職位のカードを開く →
   03のデモを1本だけ見せる → 04のスライダーを相手の実額で一緒に動かす
3. 判断で埋めた箇所の申告 — 「従業員数はHPに記載がなく採用ページから約◯◯名と想定」など
4. 変更を頼めること — 「ツールの入れ替え」「部門の追加」「試算前提の変更」は即対応できる旨

## 絶対に守ること

- **社名を書かない。** 呼称は「貴社」。URLを共有しても提案先が特定されない状態を保つ。
- **前提開示を消さない。** `company.notice` / デモの再現イメージ注記 / `roi.assumptions` /
  `next.stance` の4つは、この資料が営業パンフレットに堕ちないための装置。
- **投資額を書かない。** 提案資料の役割を奪わない。`roi.costNote` で先送りする。
- **AIが判断する話にしない。** 業務カードの `after` は人の判断で締める。
- **人員削減を示唆しない。** 削減時間は振り替え先があるものとして扱う。
- **CSS / HTML / 描画スクリプトを編集しない。** 変えるのは CONFIG と `<title>` だけ。
- **デジライズのロゴを加工しない。** 白プレート込みでヘッダー固定。ブランド4色は
  フッターのドット以外で使わない（ページの主役は提案先の色）。

## このスキルが書き込んでよい場所

- 生成物：作業ディレクトリ外（スクラッチパッド等）の一時ファイル
- `proposal-site/` 配下の更新は、ユーザーからテンプレート自体の改善を依頼されたときのみ
