# /proposal-site — 提案前フックサイト生成

営業が**提案資料を出す前**に見せる1ページのアーティファクトを作る。
目的は、提案先に「AI活用後の自社の姿」がイメージでき、費用対効果が期待できそうだと
感じてもらい、その場で質疑ができる状態にすること。**契約でも見積提示でもない。**

**目標作成時間 10分。** 迷ったら既定値で進める。完璧さより、商談に間に合うことを優先する。

## 最初に読む（必須）

**`proposal-site/knowledge/service-philosophy.md` を必ず最初に読む。**
このツールが売るのは「法人リスキリング」パッケージであり、AI活用全般ではない。
思想を外すと、作った資料がサービスと矛盾して逆効果になる。要点だけ先に：

- **「全社員が使い、リーダーが変える」= 2層同時推進**
  - Layer 1｜全社基盤 = **法人リスキリング365**（全社員／ストック）
  - Layer 2｜推進中核 = **AI人材養成講座**（推進層／6か月の研修）
- **2層は同時スタート・同時並行で垂直に立ち上げる。** 365を先に入れてから養成講座、という
  段階論ではない。「まず基盤を作ってから育成」「まず少数から」は**すべて誤り**。
  同時に立ち上げるからこそ、推進人材の成果をその時点で全社が受け取れる
- **到達レベル**が資料の中心概念
  - **Lv.1 使う** ／ **Lv.2 つくる（業務専用チャットボットを作れる）** … 365で到達
  - **Lv.3 設計する（AIエージェントを設計できる）** … 養成講座で到達
- **365は全社員に配るのが原則。**「使う人だけに配る」「少数から始める」は思想の否定
- 100名なら70名が日常利用層／30名が推進・成果創出層。**2層は段階ではなく役割分担**。
  比率そのものより、成果が全社に還る導線が通っていることが重要
- **投資額は書かない。** 公的支援2制度の存在だけ示し、金額は提案資料へ送る

## 参照ファイル

| ファイル | 読むタイミング |
|---|---|
| `proposal-site/knowledge/service-philosophy.md` | **必ず最初に** |

## 入力

- **必須**: 提案先のコーポレートサイトURL
- **任意**: 導入検討ツール（`gemini` / `copilot` / `claudecode` / `codex`）
- **任意**: 従業員数、部門構成、聞いている課題、商談相手の職位

URLだけ渡されたら**確認せずに進める**。ツール未指定なら `["gemini","copilot"]` を既定とし、
HPから Google Workspace / Microsoft 365 の手がかりが読めればそちらへ寄せる。
出力後に「ツールはこの2つにしました。変える場合は言ってください」と添える。

## 生成フロー

### 1. コーポレートカラーを抽出する

```bash
node proposal-site/scripts/brand-color.mjs <提案先URL>
```

推奨値を `CONFIG.brand.color` に使う。「△ 要調整」なら彩度を保ったまま明度を下げた同系色へ。
抽出できない／モノトーンの会社は濃紺 `#1F3A5F`。蛍光色・原色はそのまま使わない。
外部取得が失敗する環境では `WebFetch` でHPを読んで判断してよい。

### 2. HPを読んで事業を理解する

`WebFetch` で読む（あるものだけ・多くて4ページ）：

- トップ／事業紹介 — 何を作って誰に売っているか、**商材名・工程名の語彙**
- 会社概要 — 従業員数、拠点、設立
- 採用ページ — **部門構成が最もよく分かる。職種一覧が部門×職位設計の直接の材料**
- 社長メッセージ／ニュース — 直近の関心事（人手不足、技能承継など）

拾った**その会社の言葉**を以降すべての文言に使う。
読み取れなかったことは推測で埋めず「想定しました」と明記する。

### 3. テンプレートをコピーして CONFIG を書き換える

```bash
cp proposal-site/templates/proposal-site.html /tmp/<任意の名前>-proposal.html
```

出力先は作業ディレクトリ外。**テンプレート本体は上書きしない。**

書き換える順番：

1. `<title>` — 提案先の業務に即した固有名。**社名は入れない**
2. `CONFIG.brand.color` — 手順1の値
3. `CONFIG.company` — `eyebrow` / `title` / `lead` / `profile`（社名が特定されない属性のみ）。
   `notice` と `footMeta` は基本そのまま使う
4. `CONFIG.premise.facts` — HPから読み取った4項目。各項目に `src`（出典ページ名）を必ず付ける
5. `CONFIG.tools` — 検討ツールのみ残す（**3つまで**）。未選択ツールのカード・デモは自動で非表示
6. `CONFIG.levels` — **原則そのまま。** 到達レベルの定義は思想そのものなので変えない
7. `CONFIG.departments` — 5〜7部門 × 各4枚。各カードに `level` を付ける。
   `role-tasks.md` の共通カタログ＋業種固有を2〜3件
8. `CONFIG.demos` — 各層に最低1本。**チャットボット作成（base）とエージェント設計（core）**。
   普通のチャット処理はデモにしない。**自動化・半自動化のイメージが湧くことが最優先**で、
   `core` 層には `handoff`（人の工程 8→1〜2）／`runlog`（誰も操作していない稼働ログ）／
   `stats`（30日の稼働実績）を必ず入れ、承認業務なら `queue`（押せる承認ボタン）も入れる
   （`tools.md` 参照）
9. `CONFIG.roi` — `rows` の `dept` は departments の `id` と一致。`heads` 合計は従業員数以下
10. `CONFIG.qa` — 8〜10問。`roi-and-qa.md` の必須5問＋業種で選ぶ
11. `CONFIG.next` — 基本そのまま。日程が決まっていれば `when` を実日付に

### 4. 検算する（飛ばすと商談で突っ込まれる）

- [ ] **各カードの `level` と `demo` の層が一致**（Lv.1/2 → `layer:"base"`、Lv.3 → `layer:"core"`）
- [ ] カードの `tool` とデモの `tool` が一致している
- [ ] **各部門で `exec`/`mgr`/`staff` のどれを選んでも1枚以上出る**
- [ ] **商談相手の部門に Lv.3 が1枚入っている**（養成講座の価値が見えるか）
- [ ] `core` 層のデモに `handoff` / `flow` / `runlog` / `stats` がある
- [ ] `flow` の `gate`（人の判断）が2つ以上ある
- [ ] `handoff` の「人が手を動かす工程」が**0になっていない**（全自動の絵は不信を招く）
- [ ] `base` 層のデモに `builder` / `chat` / `stats` がある
- [ ] デモの表・検証結果の数字が計算上合っている
- [ ] `roi.rows` の `heads` 合計 ≤ 公表従業員数、プロフィールの「対象◯◯名」と一致
- [ ] 社名がどこにも入っていない（`<title>` 含む）
- [ ] **「少数から始める」「使う人だけ」の表現が入っていない**
- [ ] 投資額・助成金額の数字が入っていない

構文チェック（CONFIG編集で壊しやすい）:

```bash
node -e 'const s=require("fs").readFileSync("<出力ファイル>","utf8");new Function(s.match(/<script>([\s\S]*)<\/script>/)[1]);console.log("OK")'
```

### 5. アーティファクトとして公開する

`Artifact` ツールで公開。`favicon` は 🧭 固定（提案先ごとに変えない）。
`description` は「業種・規模の提案先向け／到達レベルと再現デモ」の一文。

公開後、ユーザーに渡すもの：

1. アーティファクトのURL
2. **商談での使い方**（01で理解のズレを確認 → 02で相手の職位のカードと到達レベルを開く →
   03のデモを各層1本ずつ見せ、**承認待ちキューのボタンは相手に押してもらう** →
   04のスライダーを相手の実額で一緒に動かす）
3. 判断で埋めた箇所の申告（「従業員数はHPに記載がなく採用ページから約◯◯名と想定」など）
4. 即対応できること（ツールの入れ替え／部門の追加／試算前提の変更）

## 絶対に守ること

- **「少数から始める」「基盤を作ってから育成」と書かない。** 365は全社員に配るのが原則で、
  2つのサービスは**同時に立ち上げる**。配る範囲は絞らず、
  **推進テーマと推進中核の人数を絞る**という言い方をする
- **デモは「チャットボットを作る」「エージェントを設計する」。** 普通のチャット処理は
  しょぼい印象を与えて逆効果になるため使わない
- **エージェントに人の判断（`gate`）を必ず残す。** 全自動の絵にしない
- **社名を書かない。** 呼称は「貴社」
- **投資額を書かない。** 公的支援2制度の存在だけ示す
- **前提開示を消さない**（`company.notice` / デモの再現イメージ注記 / `roi.assumptions` / `next.stance`）
- **人員削減を示唆しない。** 削減時間は振り替え先があるものとして扱う
- **CSS / HTML / 描画スクリプトを編集しない。** 変えるのは CONFIG と `<title>` だけ
- **デジライズのロゴを加工しない。** 白プレート込みでヘッダー固定。ブランド4色はフッターのみ

## このスキルが書き込んでよい場所

- 生成物：作業ディレクトリ外（スクラッチパッド等）の一時ファイル
- `proposal-site/` 配下の更新は、テンプレート自体の改善を依頼されたときのみ
